# Plan de Capacidades de Agentes y Políticas Transversales

## Contexto y Alcance
Este documento define las políticas operacionales, de reutilización de código, autoría, control de cambios y gobernanza transversal que rigen a todas las skills, agentes, hooks, herramientas y operaciones del proyecto.

## Principio de reutilización, cambios mínimos y fuentes de verdad

1. Antes de crear código, archivo, módulo, clase, función, componente, endpoint, schema, prompt, script, servicio, test, Dockerfile, configuración o dependencia, AGY debe inspeccionar el repositorio.

2. La inspección debe buscar:
   - componentes reutilizables;
   - módulos similares;
   - contratos existentes;
   - schemas;
   - utilidades;
   - validadores;
   - scripts;
   - tests;
   - fixtures;
   - Dockerfiles;
   - configuraciones;
   - documentación;
   - dependencias ya instaladas.

3. AGY debe clasificar el resultado:
   - reutilizar;
   - extender;
   - refactorizar mínimamente;
   - crear nuevo, con justificación explícita.

4. Ninguna regla de negocio, schema, contrato, constante, política de seguridad, configuración, validación, prompt versionado o fixture debe existir en más de una fuente de verdad.

5. Usar DRY correctamente:
   - evitar duplicar conocimiento y decisiones;
   - no crear abstracciones genéricas prematuras;
   - aplicar regla de tres;
   - abstraer solo si los fragmentos tienen la misma semántica, razón de cambio e interfaz clara.

6. Está prohibido crear carpetas o módulos ambiguos como:
   - utils;
   - helpers;
   - common;
   - shared;
   - generic;
   salvo justificación clara, responsabilidad definida y confirmación.

7. Antes de crear algo nuevo, el plan de AGY debe incluir:
   - qué existe actualmente;
   - por qué no se puede reutilizar;
   - qué se creará;
   - por qué el cambio mínimo no basta;
   - pruebas y documentación afectadas.

## Política estricta de autoría, commits y push

1. Está prohibido agregar firmas o referencias al agente/IA en:
   - código;
   - comentarios;
   - documentación;
   - README;
   - changelog;
   - mensajes de commit;
   - trailers;
   - coautores;
   - autor Git;
   - PRs;
   - issues;
   - releases;
   - metadatos.

2. Prohibir expresamente:
   - Generated by AI;
   - Generated with Antigravity;
   - Created by AGY;
   - Co-Authored-By;
   - Co-authored-by;
   - Assisted-by;
   - AI-assisted;
   - Claude;
   - Gemini;
   - ChatGPT;
   - OpenAI;
   - Anthropic;
   - badges, firmas o enlaces de agentes de IA no solicitados.

3. No ejecutar `git commit` sin confirmación explícita del usuario.

4. Antes de proponer un commit, AGY debe mostrar:
   ```bash
   git status --short
   git diff --staged
   git diff --check
   ```
   y debe proponer un mensaje de commit breve, convencional y descriptivo.

5. Está prohibido usar:
   - `git commit --author`
   - `git commit --trailer`
   - `git commit -s`
   - cualquier configuración o plantilla que agregue firmas automáticas sin confirmación del usuario.

6. AGY debe usar únicamente la identidad Git configurada por el usuario. Si no existe, debe detenerse y solicitar configuración humana.

7. Antes de un commit, el agente debe escanear el contenido staged y el mensaje contra firmas de IA, secretos, `.env`, credenciales, modelos, cachés y artefactos generados.

8. Está prohibido ejecutar `git push` sin una confirmación independiente, posterior y explícita del usuario, incluso si ya se autorizó el commit.

9. El hook de calidad y la skill senior-code-reviewer deben validar que no existan firmas de IA ni trailers no solicitados antes de permitir un cierre.

## Matriz de decisión reutilizar vs crear

| Situación encontrada | Acción predeterminada | Confirmación |
|---|---|---|
| Existe componente que cumple completamente | Reutilizar sin duplicar | No, salvo cambio de comportamiento |
| Existe componente extensible | Extender con cambio mínimo | Sí, si contrato público cambia |
| Hay duplicación de regla de negocio | Centralizar en fuente de verdad | Sí |
| Hay dos fragmentos parecidos, pero distinta razón de cambio | Mantener separados | No |
| Hay tres o más implementaciones con misma semántica | Proponer abstracción nombrada | Sí |
| No existe capacidad equivalente | Crear componente nuevo con justificación | Sí |
| Existe dependencia instalada que resuelve el problema | Reutilizar dependencia | No, salvo riesgo/uso nuevo relevante |
| Se requiere dependencia nueva | Justificar alternativa y tamaño/riesgo | Sí |

## Cambios para hooks futuros

El futuro hook de calidad debe:

1. Ejecutar pruebas, lint y security scan.
2. Revisar `git diff --check`.
3. Verificar que no se modificó el baseline experimental sin confirmación.
4. Buscar firmas de IA y trailers no solicitados en archivos staged y mensaje de commit propuesto.
5. Bloquear si encuentra secretos, firmas no autorizadas, CRITICAL/HIGH o comandos destructivos.
6. No permitir que una herramienta no ejecutada sea reportada como aprobada.

## Cambios para cada skill futura

Toda nueva skill debe incorporar como cláusula de cumplimiento:

- Inspección previa de reutilización antes de proponer cambios.
- Preferencia estricta por extensión o refactorización mínima de componentes existentes.
- Prohibición de duplicar fuentes de verdad (schemas, contratos, reglas de dominio, validadores).
- Aplicación rigurosa de la regla de tres contra abstracciones genéricas prematuras.
- Política de autoría y gobernanza de Git (cero firmas de IA, confirmación humana obligatoria).
- Validación activa para asegurar que no se incluyan firmas de IA ni trailers no solicitados.
